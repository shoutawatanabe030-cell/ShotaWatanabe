# 承認待ち同期ルール

`承認待ち.md` を **GitHubリポジトリ側で一元管理** するための運用ルール。
2026-09-20 より、PC側マイカンパニーフォルダ単独管理からこの運用へ移行。

#ルール #承認待ち #同期

---

## 1. 基本原則

#基本原則

1. **正本はリポジトリの `承認待ち.md`。** PC側のファイルは正本ではなく、リポジトリのクローンを参照する。
2. **読むときは必ず最新を取得してから。** 作業開始時に `git pull` する。
3. **書いたら必ず即コミット・プッシュ。** ローカルに置いたままにしない（他セッションから見えなくなるため）。
4. **1案件＝1コミット。** まとめてコミットしない（あとで「いつ誰が起票したか」を追えるようにするため）。
5. 承認・却下の結果を書き込むのも同じ手順。社長の口頭回答も、聞いた側がこのファイルに反映する。

---

## 2. PC側セッションの手順

#PC側

マイカンパニーフォルダとは別に、リポジトリのクローンを1箇所だけ持つ。

- クローン先（2026-09-21 設置・PC側はここ1箇所だけ）: `C:\Users\ryuji\repos\ShotaWatanabe`
- リポジトリ: `https://github.com/shoutawatanabe030-cell/ShotaWatanabe`
- 現在のブランチ: `claude/approval-pending-question-yjcsdb`
  （この運用が main にマージされるまでは、下の手順の `main` をこのブランチ名に読み替える）
- OneDrive の中に置くと同期がぶつかるため、クローンは OneDrive の外（上のパス）に置く

### 読むとき（承認待ちを確認する）

```
git -C <クローン先> pull origin main
```
そのうえで `<クローン先>/承認待ち.md` を読む。

### 書くとき（起票・回答反映）

```
git -C <クローン先> pull origin main
# 承認待ち.md を編集
git -C <クローン先> add 承認待ち.md
git -C <クローン先> commit -m "承認待ち: <案件名>を起票"
git -C <クローン先> push origin main
```

### マイカンパニーフォルダ側の扱い

- マイカンパニーフォルダに `承認待ち.md` の実体を置かない。リンク（ショートカット）か、クローン先への参照メモのみにする。
- 実体が二重に存在すると、どちらが新しいか分からなくなるため。

## 3. クラウド側セッションの手順

#クラウド側

Claude Code on the web のセッションは起動時にリポジトリがクローン済みなので、そのまま
`承認待ち.md` を読めばよい。書き込む場合は作業ブランチにコミット・プッシュし、
main への反映はプルリクエスト、または社長の指示で直接 main へ。

---

## 4. 記入フォーマット

#フォーマット

- ID は `AP-YYYYMMDD-01`（承認案件）、`Q-YYYYMMDD-01`（質問）。同日に複数あれば連番を進める。
- 一覧表に1行追加し、あわせて `3. 案件詳細` にテンプレートを複製して詳細を書く。
- 社長が判断したら、一覧表から外して `4. アーカイブ` に結果を1行追加し、詳細の「社長回答」に内容を記録する。
- 起票者欄には、起票したルーティン名（例: `23時ルーティン`）または担当名を書く。

---

## 5. 各ルーティンでの扱い

#ルーティン

- 社長の判断が必要になった時点で、作業を止めずに `承認待ち.md` へ起票してから次に進む。
- 起票したことは、そのルーティンの報告にも1行で書く（「承認待ちにAP-20260920-01を起票」）。
- 承認当番のルーティンは、開始時に `git pull` して一覧を読み上げる。詳細は [[ルール/承認当番]] を参照。
